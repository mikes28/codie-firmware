# Function level parity: `fw/` (C) ↔ `rust/` (Rust)

This file is the proof that the Rust port has **the same functions as the C
reconstruction** and that every one of them behaves the same way.

* The C side is `fw/include/codie.h` (the contract), `fw/modules/*.c`,
  `fw/modules/*.h`, `fw/src/*.c` and `fw/src/startup_vectors.h`.
* The Rust side is `rust/src/` (`mmio`, `hal`, `proto`, `modules`, `system`,
  `startup`, `boot`, `sim`, `state`).
* The ground truth for the *behaviour* is the original binary
  (`stm32_flash.bin`); where the C reconstruction and the binary disagree,
  the binary wins and the divergence is written down in the *note* column.
  The decompilation in `analysis/decomp/` is used as the readable form of
  the binary.

Renaming is expected and is **not** a gap: `hwiAdc_init` → `hwi_adc::init()`,
`fmt_num` → `fmt::num`, `iface_register` → `proxy::register`, … A gap is a C
function whose *behaviour* has no counterpart in the port.

| **C function symbols in total** | **238** (199 definitions + 40 weak aliases − 1 duplicate name) |

| **Gaps closed by this pass** | **3** (`sonar_busy`, `hwi_sonar` `ccer5`, the `set_afr`/`set_af` split) |
| **Gaps still open** | **0** for behaviour; 2 *divergences* where the Rust port follows the binary and the C transcription is wrong (see §4) and 2 *API-shape* divergences in `proto/` that are reported to its owner (see §5) |

## 4. Divergences where the Rust port follows the binary and the C does not

These are **not** gaps: the Rust port has the behaviour the original
firmware has. The C transcription is wrong; the binary is the ground truth.
They are listed here so that the difference is not mistaken for a port bug.

### 4.1 The empty line of the `hwiAdc` dump

* C (`fw/modules/hwi_adc.c:194`): `if (i != 0u && (i & 8u) == 0u) out_char('\n');`
* Rust (`rust/src/modules/hwi_adc.rs:99`): `if i != 0 && (i & 7) == 0 { out_char(b'\n'); }`
* Binary: `analysis/decomp/FUN_080073DC_0x080073DC.c` tests `(bVar3 & 7) == 0`,
  i.e. the empty line comes after the 9th, the 17th and the 25th value. The
  C's own comment says the same ("after 8, 16 and 24") – its mask is a typo.

**Decision:** the Rust port keeps `& 7`; the C line is the bug.

### 4.2 The `ccer5` field of the TIM17 compare channel

* C (`fw/modules/hwi_sonar.c:98`): `chan.ccer5 = 0u;`
* Rust (`rust/src/modules/hwi_sonar.rs:175`): `ccer5: 0`
* Binary: `analysis/decomp/FUN_08008F14_0x08008F14.c` builds the record with
  `FUN_0800b1d8` (which zeroes the whole `timer_chan_t`) and then sets only
  `ccmr`, `ccer`, `ccr` and `cr2` – `ccer5` stays 0.

(The drive module is the opposite case: `chan.ccer5 = 0x0008u` in
`fw/modules/hwi_drive.c:125`, `ccer5: 0x0008` in
`rust/src/modules/hwi_drive.rs:240`, and `FUN_080087D8` really does write
`local_32 = 8` – both trees agree there.)

**This pass** fixed the Rust port, which had `ccer5: 0x0008` for the sonar.
`timer::channel_cfg` ORs the field into `CCER`, and `0x0008` is `CC2E`, so the
old value enabled channel 2 of TIM17 – which the original never does.

## 5. Divergences in `rust/src/proto/` (reported to its owner)

`rust/src/proto/**` is owned by another agent, so the two items below are
reported here instead of being changed.

### 5.1 `resp_value` and a missing value

* C (`fw/modules/proxy.c:84`): `if (value != 0) { out_char(' '); out_str(value); }`
  – with `value == NULL` the reply ends after the op name.
* Rust (`rust/src/proto/proxy.rs:115`): the value is a `&str`, so the space and
  the value are always emitted.

Every caller in the C tree passes a value, so the difference is not
observable today, but the C's `NULL` case has no Rust counterpart.

### 5.2 `resp_greeting` and a NULL value in the key/value list

* C (`fw/modules/proxy.c:94`): `if (kv[i + 1] != 0) { out_str(kv[i+1]); out_char('"'); } else { break; }`
  – a NULL value breaks out of the loop and the closing quote is **not**
  written.
* Rust (`rust/src/proto/proxy.rs:147`): the pairs are a slice, the closing
  quote is always written.

The greeting of `boot::run` always has both a key and a value, so the
difference is not observable either.

## 6. How to reproduce the inventory

The C inventory is produced by scanning `fw/modules/*.c` and `fw/src/*.c` for
function definitions (a name, a balanced parameter list and a `{` after the
closing parenthesis) and expanding the `IRQ_ALIAS` macro of
`fw/src/startup_handlers.c` and the `__attribute__((weak, alias(...)))`
declarations of `fw/src/startup_stm32g071.c`. The Rust inventory is produced
by scanning `rust/src/**/*.rs` for `fn` definitions. Both numbers are in the
table at the top of this file.

`fw/` and `stm32_flash.bin` are read only; the Rust port does not add
dependencies, does not use `alloc` and does not use `std` on the target.
